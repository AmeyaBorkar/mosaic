# Mosaic Audit Sweep — 2026-07-27

**Commit audited:** `2f2f7be` (`feat(facet-abi): conformance gate — reject multi-memory in the browser`)
**Method:** two independent adversarial workflow sweeps of the same commit. Findings that
touched external-library internals (wasmtime 47.0.1) or f32 numerics were re-verified by
reading the pinned crate sources and by computing in genuine `numpy.float32` against an f64
reference; every other finding was confirmed by reading the cited source line by hand. No
finding below is asserted without file:line evidence.

> **Supersedes the first pass of this document.** The first sweep dropped two findings "on
> re-read"; the second sweep re-opened both and verified them against source. One
> (`C1`, the fuel / wall-clock DoS) was **wrongly dropped and is in fact the single most
> serious finding**; the other (`M1`, Goertzel f32 cancellation) is a real but
> regime-dependent fidelity bug. The correction is recorded here in full — see
> *Corrections to the first pass* below — because the reasoning trail matters more than a
> clean-looking result.

## Verdict

The core sandbox is sound in substance: no memory-corruption path, no sandbox escape, and no
*cross-host determinism divergence* in the arithmetic that both hosts share (relaxed-SIMD off,
NaN canonicalization on, `libm` transcendentals, no `mul_add`). But three things fail the
"no known issues shipped / treat the repo as production" bar:

1. **The authoritative (native) host has no wall-clock bound at all.** Fuel is the only CPU
   ceiling, and fuel does not meter the cost of bulk-memory instructions, so a Facet can peg
   a core for hours inside one render call (`C1`). Only the browser has a timeout.
2. **A CI / provenance hole** (`H1`): `facets/*` are excluded from the workspace and no `.wasm`
   fixture is ever rebuilt from source, so every "preview == render" proof runs against frozen
   binaries CI cannot tie to today's Facet source. Combined with no `--locked` (`H3`) and a
   floating toolchain (`H4`), the build is not reproducible and regressions land green.
3. **Several browser↔native admission-parity gaps** (`H2`, `M6`) let the browser preview a
   Facet the server would refuse — quietly weakening the admission half of "preview == render",
   including a memory64 path that bypasses the browser's 16 MiB cap.

Fix order: `C1` → (`H1` + `H3` + `H4` + `M15`) → (`H2` + `M6` parity) → the correctness
one-liners (`M7`, `M5`, `M8`, `M2`).

## Critical

### C1 — Native host has no wall-clock bound; fuel does not meter bulk-memory ops
**Category:** dos · **Location:** `crates/mosaic-runtime/src/lib.rs:82` (fuel), `:90` (no epoch)

`Sandbox` bounds guest CPU with fuel alone (`consume_fuel(true)`, `set_fuel(limits.fuel)`); no
`epoch_interruption` / `set_epoch_deadline` is configured anywhere in the repo. Verified against
`wasmtime-environ-47.0.1/src/tunables.rs:545` (`default_operator_cost`): `memory.fill`,
`memory.copy`, and `memory.init` each cost **exactly 1 fuel unit** regardless of the length
operand, charged once statically at compile time. The 16 MiB `StoreLimits` cap bounds the size of
a *single* op, but not a fuel-metered *loop* of them.

- **Failure scenario:** a Facet with a bounded 16 MiB memory whose `run` is
  `(loop $l (memory.fill (i32.const 0) (i32.const 0) (i32.const 16777216)) (br $l))`.
  Each iteration costs ~5 fuel and memsets 16 MiB. The default 100,000,000-unit budget permits
  ~20M iterations ≈ **320 TiB of writes — tens of minutes to hours of pegged CPU** in one
  `Sandbox::run_map` call that never returns early. The browser contains this with its 250 ms
  Worker terminate; the **authoritative server has no equivalent**, so `lib.rs:13`'s claim that
  runaway code "traps when the fuel is exhausted instead of hanging" is only technically true
  (it eventually traps, after hours). `SECURITY.md` scopes resource-exhaustion-past-caps as
  in-scope.
- **Fix:** enable `Config::epoch_interruption(true)`, spawn/arm an epoch ticker, and
  `Store::set_epoch_deadline` to a wall-clock backstop (the server analogue of the browser
  terminate). Keep fuel for logic bounding; add epoch for time bounding — defense in depth, not
  either/or. Add a regression test whose `run` is a `memory.fill` loop, asserting it is bounded.

## High

### H1 — CI never builds/lints `facets/*` or rebuilds any `.wasm` fixture
**Category:** ci-gap / provenance · **Location:** `.github/workflows/ci.yml:48`, `Cargo.toml:20`, `scripts/verify-fixtures.sh:17`

All six Facet crates are in the workspace `exclude` list, so `cargo test --workspace`,
`clippy --all-targets`, and `fmt --all` never touch them; the wasm32 build step names only
`glyph-atlas tessera-ascii mosaic-vm mosaic-wasm`. `verify-fixtures.sh` rebuilds and diffs only
the **4 JSON goldens**, and `emit_golden` embeds a frozen `include_bytes!` blob
(`emit_golden.rs:21,83`) rather than compiling `facets/ramp/src`. None of the 13 committed `.wasm`
fixtures is rebuilt from source.

- **Failure scenario:** edit `facets/ramp/src/lib.rs` (or a shared `dither`/`glyph-atlas` routine
  that a Facet links) and commit. `fmt`, `clippy -D warnings`, `test --workspace`, the wasm32
  build, and `verify-fixtures.sh` all pass — the last because `emit_golden` re-runs the *old*
  binary — while HEAD now contains a Facet source that does not match the binary the entire
  "preview == render" proof is measured against. `facets/*/src` is not even compile-checked.
- **Fix:** add a CI step that builds each `facets/*` for `wasm32-unknown-unknown` with the
  `--max-memory=16777216` link flag, regenerates every committed `.wasm`, and `git diff
  --exit-code`s them alongside the JSON goldens; add `clippy`/`fmt` over the facet crates.

### H2 — memory64 accepted by default (native) + browser cap bypass
**Category:** sandbox-parity / dos · **Location:** `crates/mosaic-runtime/src/lib.rs:90`, `packages/facet-abi/src/host.ts:30,66`

`Sandbox::new` disables only relaxed-SIMD, threads, and multi-memory. Verified against
`wasmtime-47.0.1/src/config.rs:2501` + `wasmparser-0.252.0/src/features.rs`: a fresh `Config`
compiles with `WasmFeatures::WASM3`, which **includes `MEMORY64`**; `compiler_panicking_wasm_features`
never removes it, so `Module::new` under this config accepts `(memory i64 …)`. wasmtime's own
`wasm_memory64` doc comment ("false by default") is stale for 47.0.1. The browser mirror's
`readUleb` reads at most 5 LEB128 bytes with 32-bit JS shifts (`0x10 << 28` wraps to 0), and
`readMemoryLimits` never inspects the is64 flag bit (bit 2), so a 64-bit memory's large maximum is
truncated below the 256-page cap and admitted.

- **Failure scenario:** a Facet declares a 64-bit memory with `max` ≈ 4.29e9 pages
  (`flags=0x05`, LEB `80 82 80 80 10`). Native: accepted; `StoreLimits::memory_size` still caps
  actual growth at 16 MiB, so it renders. Browser (Chrome/Firefox ship memory64): `readUleb`
  parses `max` as 256, `checkMemoryLimits` passes, and the Facet can `memory.grow` toward V8's
  memory64 ceiling inside the Worker before the 250 ms timer, OOMing the tab — the browser cap
  `SECURITY.md` promises is bypassed.
- **Fix:** native — `config.wasm_memory64(false)` explicitly (do not rely on the default).
  Browser — reject the is64 flag bit in `readMemoryLimits`, and make `readUleb` reject
  over-long / overflowing encodings rather than truncating.

### H3 — No `--locked` on any cargo invocation
**Category:** reproducibility · **Location:** `.github/workflows/ci.yml:42,45,48`, `scripts/verify-fixtures.sh:12-15`

Every cargo command in CI and in `verify-fixtures.sh` runs without `--locked`/`--frozen`, so Cargo
silently re-resolves and may rewrite the tracked `Cargo.lock`. CI does not test the committed
dependency graph, and a `cargo build --locked` from the same commit is not guaranteed to
reproduce it.

- **Failure scenario:** `wasmtime = "47"` (the sandbox itself) publishes 47.0.x with a change to
  trap delivery or `StoreLimits` accounting; every CI run silently builds against the new patch.
  Symmetrically, a `libm 0.2.x` bump shifts a transcendental and `verify-fixtures.sh` regenerates a
  golden from the new libm, turning an unpinned-dependency drift into a "goldens are stale" failure
  on a PR that changed nothing.
- **Fix:** add `--locked` to every cargo invocation in CI and the fixture script.

### H4 — Floating `stable` toolchain masquerading as pinned
**Category:** reproducibility · **Location:** `rust-toolchain.toml:1-3`

`channel = "stable"` under the comment "Pins the toolchain so every machine builds Mosaic
identically"; `README.md:112` likewise says "pinned". `stable` resolves to whatever release is
current, so committed `.wasm` bytes are not reproducible (different rustc/LLVM ⇒ different
codegen), and — combined with `clippy -D warnings` — a new lint on a future stable retroactively
fails every commit in history, defeating `git bisect` and CONTRIBUTING's bisectability bar.

- **Fix:** pin an explicit version (`channel = "1.NN.0"`) and bump it deliberately; or drop the
  "pinned" wording and add the CI rebuild-and-diff gate (`H1`) so a codegen change is caught, not
  silently absorbed.

### H5 — No dependency / supply-chain audit anywhere in CI
**Category:** supply-chain · **Location:** `.github/`

`.github/` contains only `ci.yml` — no `cargo-audit`/`cargo-deny`, no dependabot, no advisory or
license scan — in a repo whose stated purpose is executing untrusted third-party code on wasmtime.

- **Failure scenario:** a RUSTSEC advisory lands against `wasmtime 47.x` (historically a real
  class of bug); nothing in the repo notices, and with the unenforced lock (`H3`) CI keeps building
  the vulnerable version, silently falsifying `SECURITY.md`'s containment guarantee.
- **Fix:** add a `cargo-deny` (advisories + licenses + bans) CI job and a dependabot config.

### H6 — Unbounded STFT window: `hann(win)` allocates with no upper cap
**Category:** dos · **Location:** `crates/tessera-spectral/src/lib.rs:220,364`

`SpectroGrid::new` clamps `win` with a floor only (`win.max(1)`); `check_feature_budget` bounds
`frames × bands`, not `win`. A tiny signal with a huge `win` passes every guard and then drives an
unbounded `Vec<f32>` in `hann(win)`.

- **Failure scenario:** `extract_spectral_features(samples=8, sample_rate=8000, bands=1,
  win=4_000_000_000, hop=1, …)` — `frames=1`, budget OK — then `hann(4e9)` requests ~16 GB: on
  wasm32 `Layout::array::<f32>` overflows 32-bit `usize` and traps the module; natively it aborts
  the render process. Reachable through the public `extract` API and the wasm-bindgen wrapper.
  (The Goertzel *cost* is likewise `frames × bands × win`, so `win` also needs a work bound.)
- **Fix:** validate `win`/`hop` against a `MAX_WINDOW` before `hann`, returning
  `Error::InvalidWindow`; mirror the byte-budget pattern already used for the feature buffer.

## Medium

### M1 — Goertzel `power` catastrophically cancels in f32 near DC
**Category:** correctness · **Location:** `crates/tessera-spectral/src/lib.rs:386`

`power = s1*s1 + s2*s2 - coeff*s1*s2` is `|X|²`, but with `coeff → 2` (band centre near DC) it is
a difference of near-equal large terms. Verified in `numpy.float32` against f64: the DC witness
(fs=8000, win=16384, DC input, fc=1 Hz) gives f32 `mag = 160.0` vs f64 `59.7` — **167.9% error**.
Both hosts run the same f32 ops, so this is a *shared fidelity bug, not a preview≠render split*.
Rendering impact is regime-dependent: because the grid is peak-normalized (`:396`), the garbage
low band only corrupts output when its true energy rivals the real peak — a "strong DC/low-freq +
tone" signal — where it becomes the false global peak and **flips which band renders brightest**
(constructed `DC + 0.021·sin(440 Hz)`: near-DC and 440 Hz cells both change glyph vs the f64
reference). Not universal, but real.

- **Fix:** accumulate the final power in f64, or use the non-cancelling
  `re = s1 - s2·cos(w)`, `im = s2·sin(w)`, `mag = hypot(re, im)`.

> This finding and `C1` were **dropped by the first pass of this audit**; both were re-verified
> and re-instated. See *Corrections to the first pass*.

### M2 — Untrusted-output filter passes U+2028/2029 and zero-width/format/combining
**Category:** injection · **Location:** `crates/mosaic-core/src/lib.rs:210`

`is_unsafe_glyph` masks `char::is_control()` (Cc/C1 only) + the bidi set, so **U+2028/U+2029
(Zl/Zp)** slip through, as do ZWSP/ZWNJ/ZWJ (U+200B–200D), U+2060, U+FEFF, and combining marks (Mn).
The module doc claims "Only printable glyphs cross the boundary" and masks LF/CR because they
"break the row/column grid".

- **Failure scenario:** a Facet emits U+2028 — inert in a terminal, but a forced line break when the
  artifact renders in a `<pre>` on the web shell (CSS Text 3 counts it as a newline), and a syntax
  break inside a generated JS string. Every row still reports the right `chars()` count while the
  visual grid is destroyed. Combining marks stack (Zalgo) and overflow the artifact box.
- **Fix:** add U+2028/2029, the zero-width/format set (U+200B–200D, U+2060, U+FEFF), and a
  combining-mark bound to the mask.

### M3 — `run2d` propagation Facets have no browser sandbox/timeout
**Category:** dos / parity · **Location:** `packages/facet-abi/src/worker.ts:8`, `sandbox.ts:42`

`worker.ts` imports only `runFacetMap` (1-D); `runFacetSandboxed` has no 2-D branch, and
`runFacetMap2d` in `host.ts` has no Worker wrapper. `compileFacet` accepts a `run2d`-only module
(`host.ts:146`), so the only way to run one in the browser is the synchronous, unpreemptable
`runFacetMap2d` on the caller's thread.

- **Failure scenario:** a never-returning `run2d` Facet (the `spin` fixture pattern, ported to
  `run2d`) run via `runFacetMap2d` freezes the tab permanently — the exact hazard the
  Worker+timeout exists to prevent (`docs/architecture.md:220` claims "the propagation path
  inherits every sandbox guarantee").
- **Fix:** add a 2-D branch to `worker.ts` / `runFacetSandboxed` that dispatches to
  `runFacetMap2d`.

### M4 — DSL/interp Facets have no browser execution path
**Category:** parity / doc-drift · **Location:** `packages/facet-abi/src/host.ts:167`

The browser host mirrors `run_map` only; `load_program` appears nowhere in `packages/`, so the
interpreter Facet can never be given a bytecode program in the browser.

- **Failure scenario:** an author writes `ramp(luma, " .:-=+*#%@")`. Server-side `run_program`
  loads the program and renders. Browser-side, `runFacetMap` instantiates `facet_interp.wasm` and
  calls `run` with no program loaded; the guest hits `PROG_OK == false` and traps. Every DSL-authored
  Facet **fails preview while the authoritative render succeeds** — a total divergence for the whole
  DSL class, contrary to README's "proven end-to-end, native and browser".
- **Fix:** implement a `load_program`-carrying browser entry point (mirroring
  `Sandbox::run_program`), or scope the README claim until it exists.

### M5 — Two ramp-index formulas disagree at exactly one f32 luma
**Category:** determinism · **Location:** `crates/tessera-ascii/src/lib.rs:615`

Native `render_ascii::density_glyph` uses `(l*(n-1)).round() as usize`; `facets/ramp/src/lib.rs:92`
(and the spectral engine, the DSL, and the DSL test) use `(l*(n-1) + 0.5) as usize`. Verified by an
exhaustive scan of all **1,065,353,217** representable f32 in [0,1] for the real RAMP length (10):
there is **exactly one** divergent luma, `0x3D638E38` (≈0.05555555), where native → `' '` and the
Facet → `'.'`.

- **Failure scenario:** a cell whose mean luminance is exactly that f32 renders as `' '` through
  `render_ascii` and `'.'` through the sandboxed/browser Facet, breaking the byte-identical contract
  `crates/tessera-ascii/tests/sandboxed_facet.rs` asserts. Astronomically rare by chance (why the
  random-image test passes by luck) but adversarially constructible, since untrusted images control
  pixels, and a byte-for-byte contract is binary.
- **Fix (one line):** change `:615` to the `+ 0.5` truncation form every other path already uses;
  ideally hoist one shared ramp-index helper into `mosaic-core`.

### M6 — Browser↔native admission-parity gaps
**Category:** parity · **Location:** `packages/facet-abi/src/host.ts:122,232,158,96`

Four classes where the browser **accepts a Facet the server rejects**, breaking the admission half
of "preview == render":

- **No `table_elements` cap** — native `StoreLimits.tables(1).table_elements(10_000)`; the browser
  never inspects the table section, so a `(table 20000 funcref)` Facet previews and the server
  refuses it (`map_contains_table_bomb`).
- **Export check is arity-only** — `alloc.length`/`run.length` is `Function.length`, carrying no
  type info; the native `get_typed_func::<(i32,i32,i32,i32),()>` checks parameter *and* result
  types. A wrong-signature Facet previews (possibly with wrong tokens if params are `f32`) and fails
  render.
- **No module-byte cap** — native rejects modules > 8 MiB before Cranelift; the browser hands
  arbitrary-length bytes to `WebAssembly.compile`.
- **Atomics accepted** — native `wasm_threads(false)` rejects *all* atomic instructions at
  validation; the browser checks only the shared-memory bit, so `i32.atomic.rmw.*` on non-shared
  memory previews and fails render.
- **Fix:** extend `validateFacetModule`/`checkMemoryLimits` to enforce a table-element cap, a
  module-byte cap, and to reject atomics; validate the guest ABI signatures by type where the
  binary format allows, not by arity alone.

### M7 — `Canvas::place` uses unchecked `i32` offset arithmetic
**Category:** dos / correctness · **Location:** `crates/mosaic-core/src/lib.rs:468,473`

`let cr = lr as i32 + row_off;` / `let cc = lc as i32 + col_off;` with `row_off`/`col_off` from
untrusted Composition JSON (`Placement`) and the JS `Canvas.place` binding.

- **Failure scenario:** `"at": {"row": 2147483647}` on a ≥2-row layer → `1 + i32::MAX` **panics
  under overflow-checks** (dev/test *and* `wasm-pack --dev`, both used by CI) and wraps in release,
  so the two hosts disagree on the failure mode. The doc two lines up promises offsets "may push the
  layer partly off-canvas; only in-bounds cells are affected".
- **Fix:** compute the target coordinate in `i64` (or `checked_add`) before the bounds test.

### M8 — DSL table/glyph-set length truncated to `u16`
**Category:** correctness · **Location:** `crates/mosaic-dsl/src/lib.rs:671`

`b.extend_from_slice(&(t.len() as u16).to_le_bytes())` truncates before `mosaic_vm::validate` sees
it, while the full payload is still emitted. A ≥65 536-char glyph string writes length 0 and
desyncs the program's sections, so `validate` reads the code section from inside the
attacker-controlled table payload.

- **Failure scenario:** a crafted 65 536-char literal makes `validate` accept a tiny program
  assembled from the payload bytes, so `compile` returns `Ok` for bytecode that has nothing to do
  with the human-readable source — defeating the "shareable, inspectable program" premise. (This is
  an integrity/source-fidelity break, not a memory-safety escape: `validate` still guards `run`.)
- **Fix:** reject `t.len() > MAX_TABLE_LEN` (and any `> u16::MAX` params/tables count) as a clean
  positioned `CompileError` *before* the cast.

### M9 — Cranelift compilation cost is unbounded
**Category:** dos · **Location:** `crates/mosaic-runtime/src/lib.rs:44,106`

`MAX_MODULE_BYTES` (8 MiB) bounds input bytes, not compile cost. `StoreLimits` is built in
`fresh_store` *after* `Module::new`, so it never bounds Cranelift, and `parallel_compilation`
defaults true (verified `config.rs:306`).

- **Failure scenario:** an 8 MiB module dominated by a huge `br_table` builds a CFG with millions of
  edges in one function; Cranelift runs dominator/liveness/regalloc over it with no fuel/epoch/memory
  ceiling on the compile phase, saturating every core.
- **Fix:** cap function/section counts pre-compile (a cheap structural pre-pass), and/or run
  `Module::new` under the epoch deadline added for `C1`.

### M10 — TypeScript is never type-checked
**Category:** ci-gap · **Location:** `.github/workflows/ci.yml:79`, `packages/facet-abi/tsconfig.json`

`tsconfig.json` declares `strict` + `noUncheckedIndexedAccess`, but no `typescript`/`@types/node`
dependency is declared and no CI step runs `tsc --noEmit`; `node --test` only strips types. The
security-critical browser host has zero static checking.

- **Failure scenario:** a change to `host.ts` reads a possibly-`undefined` memory descriptor field

**Category:** dos · **Location:** `crates/mosaic-compose/src/lib.rs:184`

## Corrections to the first pass

The first pass of this document dropped two findings "on re-read". Both were wrong to drop:

- **C1 (fuel / wall-clock).** First-pass reasoning: "the 16 MiB memory cap bounds each bulk-memory op
  to microseconds." That considers a *single* op; it misses the fuel-metered *loop* (each
  `memory.fill` is 1 fuel but O(16 MiB) work, and 100M fuel buys ~20M of them). Re-verified against
  `wasmtime-environ-47.0.1`. **Upgraded from dropped → Critical.**
- **M1 (Goertzel).** First-pass reasoning: "textbook-correct magnitude; not a static defect —
  worth a quick empirical f32 check." That empirical check was run (`numpy.float32` vs f64) and shows
  a 167.9% error at a near-DC band with a real render consequence in the "strong DC + tone" regime.
  **Re-instated as Medium.**

The truth-telling lesson: a formula being *algebraically* correct (`s1²+s2²−coeff·s1·s2`) says nothing
about its *numerical* behaviour in f32, and a per-op cost bound says nothing about a per-call cost
bound. Both dismissals conflated the two.

## Method

Two independent 9–10-dimension adversarial sweeps of `2f2f7be` (sandbox-native, sandbox-browser,
vm-validator, determinism, engines, composite-compose, dsl-compiler, ci-hygiene, doc-drift). 66 raw
findings in the second sweep; deduped to the distinct set above. External-library and numeric claims
were re-verified by reading the pinned crate sources (wasmtime/wasmparser 47.0.1 / 0.252.0) and by
f32/f64 computation; all others by reading the cited source line. Nothing is asserted here that was
not confirmed on a direct read.
